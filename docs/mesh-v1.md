# TodeX device groups (mesh v1)

Status: normative for phase 1 (identity, groups, joining, approval on the
clients, history in one step). Implemented by `TodeX_backend` (`src/mesh/`,
`src/server/mesh.rs`), `TodeX_protocol` (`src/mesh.ts`, the pairing
extensions in `src/devicePairing.ts`) and the desktop and web clients. All
implementations pass `TodeX_protocol/tests/fixtures/mesh-v1.json`
(generated by `TodeX_protocol/scripts/generate-mesh-v1-vectors.cjs`; the
backend keeps a verbatim copy in `tests/fixtures/mesh-v1.json`).

A group is a set of backends ("nodes") and client devices that trust each
other without a central server. A device that joins a group once can reach
every backend of the group and read its history; joining is approved on any
device already in the group, never on a backend. Point-to-point pairing
([device-verification.md](device-verification.md)) is unchanged and keeps
working next to groups.

Later phases (address tables and re-joining after network changes, relaying
through members) build on the records defined here and are not part of this
version.

## Encoding and primitives

- base64url without padding (`b64u`) for every binary value.
- Signatures: Ed25519, verified strictly (`verify_strict`: small-order keys
  and non-canonical signatures are refused).
- Hash: SHA-256. HMAC: HMAC-SHA256. KDF: HKDF-SHA256.
- Times are Unix milliseconds.

## Identities

| Who | Key | Id |
|---|---|---|
| Device (client) | Ed25519 group member key, one per device and group | `dev_` + b64u(SHA256(pk)[0..12]), the same derivation as device auth |
| Node (backend) | Ed25519 node key, one per data directory, `mesh/node-key.json` | `node_` + b64u(SHA256(pk)[0..12]) |
| Recovery | Ed25519 seed = HKDF(salt = `"todex.mesh.v1"`, ikm = recovery seed, info = `"todex.mesh.v1/recovery-signer"`, 32) | `recovery` |

The device member key is also the device-auth key the device signs requests
with on every node of the group, so a node authenticates group members
exactly as paired devices. Each device member also has an X-Wing history
key (history v3 recipient, [history-encryption.md](history-encryption.md)).
The recovery seed is the existing 24-word recovery key: its X-Wing key is
the history recovery recipient, the key derived above signs roster changes
when no device is left.

`node-key.json` is `{"version":1,"secretKey":"<b64u 32-byte seed>"}`, mode
0600, created on first start. It is not the transport key: resetting the
transport encryption keeps the node id.

## Signed documents

A signed document is `{"body": b64u(json bytes), "sig": b64u(signature)}`.
The signature covers `domain || json bytes`; readers parse the JSON from
the exact bytes that were signed and never re-serialize. `hash(doc)` is
`SHA256(json bytes)`.

| Document | Domain |
|---|---|
| Roster | `todex.mesh.v1/roster\0` |
| Node info | `todex.mesh.v1/node-info\0` |

Bodies are at most 256 KiB. Unknown fields are ignored.

### Roster

```json
{
  "type": "todex.mesh.roster", "v": 1,
  "groupId": "grp_…",            // null in the genesis document
  "version": 3,                   // 1 for the genesis document
  "prev": "<b64u hash of version 2>", // null in the genesis document
  "nonce": "<b64u 16 bytes>",     // genesis only
  "name": "Home",
  "signer": "dev_…",              // or "recovery"
  "signedAt": 1767225600000,
  "recovery": {"signingKey": "<b64u Ed25519>", "historyKey": "<b64u X-Wing>"}, // or null
  "members": [
    {"id": "dev_…", "kind": "device", "name": "MacBook", "publicKey": "<b64u>",
     "historyKey": "<b64u X-Wing>", "addedAt": 1767225600000, "addedBy": "dev_…"},
    {"id": "node_…", "kind": "node", "name": "nas", "publicKey": "<b64u>",
     "addedAt": 1767225600000, "addedBy": "dev_…"}
  ]
}
```

`groupId = "grp_" + b64u(SHA256(genesis json bytes)[0..16])`.

A roster chain is the list of documents from the genesis to the head. It is
valid when:

1. Document `i` (from 1) has `version = i`. The genesis has `groupId` and
   `prev` null and a 16-byte `nonce`; every later document has the chain's
   `groupId` and `prev = b64u(hash(document i-1))`.
2. The genesis is signed by a device member it lists. A later document is
   signed by a device member of the previous document, or by `recovery`
   with the previous document's `recovery.signingKey`. The signer of a
   document can therefore never be someone that document's predecessor did
   not list: a removed device cannot sign again.
3. Every document lists 1–256 members with unique ids, at least one device.
   Each id matches its kind and public key (prefix and derivation above).
   Device members carry a 1216-byte `historyKey`; node members carry none.
   Names follow the device-name rules of pairing v3 (1–80 scalars, no
   control or bidi formatting characters, no surrounding whitespace).
4. The chain has at most 4096 documents.

Concurrent edits can fork a chain. Every reader keeps exactly one chain per
group and replaces it with another valid chain of the same group when the
other is longer, or of the same length with a head hash that is smaller
(bytewise). A client whose change lost re-applies it on the chain that
won.

### Node info

```json
{"type": "todex.mesh.node-info", "v": 1, "nodeId": "node_…", "publicKey": "<b64u>",
 "seq": 1767225600000, "name": "nas", "transportProtocol": "ml-kem-768",
 "transportPublicKey": "<b64u>", "urls": ["http://192.168.1.20:7345"],
 "signedAt": 1767225600000}
```

Signed by the node key. Readers accept it only for a node member of the
group whose `publicKey` equals the roster entry, and keep the highest `seq`.
`transportProtocol`/`transportPublicKey` are what the node's transport v2
handshake uses (they change when the transport keys are reset); a client of
the group pins them as if device pairing had delivered them
(`transportVerified`). `urls` are the node's own view of its addresses
(`advertise_url` first, then the listener's interface addresses); at most 16.
A node signs a new info document whenever any field changes, with
`seq = max(previous seq + 1, now)`.

## Joining a group

Joining reuses device pairing v3 (`/v2/device-pairing/create`, `reveal`,
`poll`, `cancel`, [transport-v2.md](transport-v2.md)). Its transcript,
verification code and keys are unchanged; `create` takes an extra `mesh`
object and the credential carries extra fields. A request with `mesh` is
never shown to the backend's local approver (TUI, `pair list`) and never
writes `devices.json`.

### A device joins

The new device holds an invite (below) and pairs with any reachable node of
the group:

```json
"mesh": {"kind": "deviceJoin", "groupId": "grp_…",
         "historyKey": "<b64u X-Wing>", "historyKeySignature": "<b64u>"}
```

`historyKeySignature` is the device member key's Ed25519 signature over
`"todex.mesh.v1/history-key\0" || groupId || "\0" || historyKey bytes`. It
binds the history key to the device key the verification code covers. The
node answers `404 NOT_FOUND` when it is not in that group and `400` when
the signature does not verify.

After `reveal` the request is listed to the group's devices
(`mesh.join.list`, pushed as `mesh.updated` with reason `join.requested`).
Any device of the group shows the name, device id, peer address and the
verification code; the user compares the code with the new device. To
approve, the device appends a roster version that adds the new device
(`kind: "device"`, the request's public key and history key, `addedBy` =
the approver) and sends `mesh.join.approve {requestId, chain}`. The node
accepts the chain (rules below), checks that its head lists the request's
device with exactly that public key and history key, and marks the request
approved. `mesh.join.reject {requestId}` rejects it. The first decision
wins; the request disappears from every device's list (`join.decided`).

The poll credential is the usual `{deviceId, transportProtocol,
transportPublicKey}` plus `"groupId"`. The new device then connects to the
node with its member key, reads the group (`mesh.state.get`), verifies the
chain from the invite's `groupId` and checks that the head lists itself.

### A node joins

A node that is to join a group shows a join code: 16 characters of the
RFC 4648 base32 alphabet (80 bits), displayed `XXXX-XXXX-XXXX-XXXX`, valid
24 hours and for one successful join. Readers normalize input by
uppercasing, dropping `-` and whitespace and mapping `0→O`, `1→I`, `8→B`.
`codeKey = SHA256("todex.mesh.v1/join-code\0" || normalized code)`.

A device of the group pairs with the node and proves it knows the code:

```json
"mesh": {"kind": "nodeJoin", "groupId": "grp_…"}
```

`create` answers with the usual fields plus `"nodeId"` and
`"nodePublicKey"`. `reveal` carries
`"joinCodeProof": b64u(HMAC(codeKey, "todex.mesh.v1/node-join/client\0" || SHA256(transcript)))`.
The node checks it in constant time. A wrong proof answers `401` and drops
the request; after 5 wrong proofs the code is discarded. A right proof
approves the request at once, consumes the code and admits the device's
key for 10 minutes. The credential adds `"groupId"`, `"nodeId"`,
`"nodePublicKey"` and
`"joinProof": b64u(HMAC(codeKey, "todex.mesh.v1/node-join/server\0" || SHA256(transcript) || nodePublicKey bytes))`.
The device checks `joinProof`; only then does it trust the node key and
the transport key. Someone in the middle sees neither the code nor a way to
test guesses offline faster than 2^80.

The device then appends a roster version that adds the node
(`kind: "node"`) and sends it with `mesh.state.push` over the new
connection, which authenticates with the admitted key. Once the node
accepted a chain that lists it, the admission ends and the group roster
authorizes the device.

A device already paired point-to-point with a node (including the desktop's
own local backend) can add that node without a code: it reads the node's
key with `mesh.node.get` and pushes a chain that lists the node. Any device
the node already trusts may do this, because a paired device controls that
backend fully anyway.

Join codes come from `todex-agentd mesh join-code [--new]`, from the TUI,
from `POST /v2/local-admin/mesh/join-code` (IPC only), and from the log at
startup when the node is in no group. The code lives in
`mesh/join-code.json` (0600).

### Invite

What a device of the group shows (QR code or link) to a new device:

```json
{"kind": "todex-mesh-invite", "version": 1, "groupId": "grp_…", "name": "Home",
 "nodes": [{"nodeId": "node_…", "name": "nas", "urls": ["http://192.168.1.20:7345"]}]}
```

An invite carries no keys or secrets. The new device tries the nodes in
order until one answers; the verification code then authenticates the node
it reached.

## Node behavior

### Accepting a chain

`mesh.state.push` and `mesh.join.approve` carry a full chain. A node:

- verifies it (rules above);
- for a group it is in, keeps the stored chain unless the new one wins the
  fork rule; a chain whose head no longer lists the node removes the node
  from the group (its stored group state is deleted);
- for a group it is not in, joins only when the head lists its own node id
  and key, and only for a caller it already trusts (a paired device, a
  member of another of its groups, or an admitted key);
- answers `{"groupId", "version", "head", "changed"}`.

`nodeInfos` sent with `mesh.state.push` are verified and stored for other
nodes of the group (highest `seq` kept); a node never stores its own.

### Authorization

The device registry the node authenticates against is `devices.json`, then
the device members of every group the node is in, then admitted keys. A
device removed from every group fails authentication on its next request,
and its open sockets close within 5 s (`4401`), as for a revoked device.
History access follows: the history registry revokes the recipient of a
device that the registry no longer knows and blocks the device
(`revokedBy: "local"`). A device that is removed and later joins again uses
a new member key.

### History

When an accepted chain lists a device with a history key that is not yet a
recipient, the node registers it (`recipient.registered`) and opens a grant
for it (`grant.requested`). Any device of the group that is connected and
holds history keys fulfills such a grant without asking, as the approval
already covered history. When the chain carries `recovery.historyKey` and
the node has no active recovery recipient, the node sets it
(`recovery.set`); an existing recovery recipient is left alone.

### State

`mesh/` in the data directory, every file 0600, written atomically:

- `node-key.json`
- `groups/<groupId>.json`:
  `{"version":1,"chain":[SignedDoc…],"nodeInfos":{"node_…":SignedDoc}}`
- `join-code.json`: `{"code","createdAt","expiresAt"}`

## WebSocket commands

All require an authenticated device. Mesh needs device auth: with
`enable_auth = false` every command answers `UNSUPPORTED`.

| Command | Request | Response |
|---|---|---|
| `mesh.node.get` | `{}` | `{nodeId, nodePublicKey, nodeInfo, groups: [groupId…]}` |
| `mesh.state.get` | `{groupId?}` | `{nodeId, nodeInfo, groups: [{groupId, chain, nodeInfos: [SignedDoc…]}]}` |
| `mesh.state.push` | `{chain, nodeInfos?}` | `{groupId, version, head, changed}` |
| `mesh.join.list` | `{}` | `{requests: [{requestId, groupId, verificationCode, deviceName, deviceId, devicePublicKey, historyKey, peerAddress, origin?, viaProxy?, expiresAt}]}` |
| `mesh.join.approve` | `{requestId, chain}` | `{approved: true, groupId, version}` |
| `mesh.join.reject` | `{requestId}` | `{rejected: true}` |

Errors: `INVALID_REQUEST` (malformed or invalid chain), `NOT_FOUND`
(unknown group or request), `CONFLICT` (request already decided, or a chain
that loses the fork rule for `mesh.join.approve`), `FORBIDDEN` (joining a
group for a caller the node does not trust).

### Event `mesh.updated`

Broadcast to every `/v2/ws` connection after a change was stored:
`{reason, groupId, requestId?, version?}` with `reason` one of
`join.requested`, `join.decided`, `roster.updated`, `node-info.updated`,
`group.left`. Clients re-read with `mesh.state.get` / `mesh.join.list`.

## Version

`/v2/version` reports `"mesh": 1`. Clients hide group features for a
backend that does not.

## Limits of this version

- Removing a member takes effect on a node when that node receives the new
  chain. A node that is offline then keeps accepting the removed device
  until a device of the group pushes the chain to it.
- Removing a device from a group does not revoke a separate point-to-point
  pairing of the same physical device; those use other keys.
- A grant for history on a node is fulfilled only once some device that
  holds history keys for that node connects.
